# Todoist Kickoff Prompt

Turn Todoist tasks into self-contained prompts that a fresh Claude Code (or any agent) can pick up cold and start executing. Designed as the post-triage handoff — once a task is dated and homed, the kickoff prompt is what you actually paste into a session to start work.

## Prerequisites

- `td` CLI installed and authenticated
- Task IDs in hand (either user-selected or auto-suggested per Step 2)

## Workflow

### 1. Take input

Two trigger modes plus a preview flag:

| Mode | Signal |
|---|---|
| **Explicit** | User names task IDs ("kickoff prompts for `6abc...` and `6def...`") |
| **Auto-suggest** | Caller (triage skill) hands over a candidate list, OR user says "generate prompts for high-impact items" |
| **`--dry-run`** | Print prompts to terminal only; **skip the description append**. Use when user wants to preview format/quality before committing the writes. Default is print+append. |

When auto-suggesting, present the candidate list before generating prompts — the user should be able to add/remove IDs.

### 2. Auto-suggest signals (when not explicit)

Score each task; flag for prompt generation if it has ≥2 signals:

- **Cold-start refs in description** — file paths (`docs/`, `src/`, `~/`), bead IDs (`bd-XXX`), ADR paths, memory file refs, URLs to internal docs
- **Acceptance criteria present** — `Acceptance:`, `AC #N`, `- [ ]` checklists, "Decisions to make" sections
- **Dated within 7 days** OR **overdue** — has near-term action pressure
- **Priority P1 or P2** — high-leverage items
- **"How to pick back up" / "Next concrete action" / "Action" section** — explicit kickoff guidance

Skip:
- **Bare-title tasks** with no description — there's nothing to kickoff from
- **Trivial one-clicks** ("install X.dxt", "create Y account") — prompt would be padding
- **Tasks with `## Kickoff` section already in description** — already done

### 3. Read full task

Always `td task view <id>` before generating — list-view truncates descriptions.

```bash
td task view 6abc...
```

Batch in parallel for multiple IDs.

### 4. Generate the prompt

Template:

```markdown
## Kickoff: <task title>

**Task:** <Todoist URL>
**Due:** <date> · **Priority:** P<n> · **Project:** <project name>

### Goal
<one-sentence goal extracted from description>

### Why now
<rationale: blocker unblocked / N days overdue from <session> / gating <downstream> / deadline pressure>

### Cold-start refs
- **Files:** <paths from description>
- **Beads:** <bd-IDs and their relationships>
- **ADRs / docs:** <paths>
- **Memory:** <relevant memory files>
- **Sessions:** <prior session journal entries>

### Acceptance
- [ ] <criterion 1>
- [ ] <criterion 2>

### Next concrete action
<the "How to pick back up" / "Action" section from description, condensed to the FIRST step only>

### Decisions to make (if any)
- <decision 1, pre-answered if the task description implies an answer: "if X, do Y">
- <decision 2>

### Autonomy
- Done = <live-verified endpoint: merged + deployed + observed working, naming the metric/surface — or, if a review gate applies, "PR open + CI green + review clean; operator merges">
- Verify the task's premise against the live system before executing; if stale, note it and proceed from reality.
- At unlisted design forks: pick the reversible option consistent with linked docs, record the rationale, keep going. Stop only for irreversible actions, new spend, product/positioning calls, or schema/contract changes.

---
*Generated by `todoist-kickoff-prompt` from task `<id>`*
```

**Extraction rules:**
- **Goal:** Use the first sentence of description, or the task title if description leads with context.
- **Why now:** See the recipe below — combine due-date math + session-of-origin extraction.
- **Cold-start refs:** Pull every `docs/`, `src/`, `~/`, `bd-XXX`, URL, and memory-file mention from the description. Don't hallucinate — only what's actually written.
- **Acceptance:** Look for `Acceptance:`, `AC`, `- [ ]`, "Decisions to make", "Open questions" sections. Convert to checklist.
- **Next concrete action:** Find the **first numbered step** in any "How to pick back up", "Action", or "Steps" section. Truncate at the first step — the prompt is for kickoff, not full execution.
- **Autonomy:** Always include. Derive the "Done =" line from the acceptance criteria's strongest verifiable endpoint (prefer live-verified over PR-open). Pre-answer any decision the task description already implies an answer to — every pre-answered fork is a mid-session stall avoided. The fork/stop-rule lines are boilerplate; keep them verbatim.

If a section can't be filled from description content, **omit the section** rather than padding. A 5-section prompt with real content beats an 8-section prompt with `<placeholder>`.

**Prompt-shape rules** (empirical, Cursor research 2026-07 — shape every generated prompt this way):
- **Constraints beat instructions**: "no TODOs, no partial implementations, never weaken a failing gate" outperforms "remember to finish".
- **Numeric ranges beat vague scope**: if the task involves generating/enumerating (tasks, tests, findings), give a range ("add 5–15 test cases"), never "add tests" or "several".
- **Acceptance is the floor, not the ceiling**: the checklist defines done; repo quality gates and obvious adjacent correctness still apply even though unlisted. Say so when acceptance is sparse.
- **Exit conditions, never pressure**: keep the "Done =" endpoint concrete; never emit "keep working until done" / "do not stop" phrasing — it measurably increases faked passes and weakened tests.

#### "Why now" computation recipe

The single hardest field to do well — drives whether the prompt feels urgent or ignorable. Combine three sources:

1. **Date math** — compute `today - due_date` (or `due_date - today` if future). Render as:
   - Past: `"N days overdue"` if N>0
   - Today: `"due today"` 
   - Soon: `"in N days"` if 1≤N≤7
   - Far: omit the date phrase; use the gating reason instead

2. **Session-of-origin extraction** — scan description for `YYYY-MM-DD` or "from <date>" or "<date> session" references, prefer the **earliest** date mentioned. That's typically when the work was scoped. Compute `today - earliest_session_date` for the "stale since" framing.

3. **Gating reason** — find the explicit blocker/dependency phrase: `"blocks bd-XXX"`, `"prereq for Phase N"`, `"gates downstream X"`, `"blocked on Y"`. This is the *why-this-is-actually-load-bearing* signal.

**Compose:** prefer the gating reason if present; fold in date math if useful; mention session origin if the gap is >7 days.

Examples:
- `"10 days overdue from 2026-04-29 PRD review session. Phase 1 ship gated on this sign-off."` (all three: math + session + gate)
- `"P0.1 prereq blocking bd-6p51 Phase 1. Higher-yield-per-effort lever than VC scraping if true."` (gate-only — date is implicit in the schedule)
- `"4 days overdue; consolidated into 5/11 review block. Direct ask needed before VC scraper bd-6p51.3 can use the expanded set."` (math + downstream gate)

Avoid: `"Review pending."`, `"Needs attention."`, `"Should be done."` — these are content-free filler. If you can't compute a real "why now", **omit the section** entirely.

### 5. Output: print AND append

**Print to terminal:** full prompt block, ready to copy.

**Append to task description:** add a `## Kickoff Prompt` section at the bottom of the existing description so it lives with the task in Todoist UI.

```bash
# Read existing description
existing=$(td task view "$id" | sed -n '/^Description:/,$p' | tail -n +2)

# Compose new description with appended kickoff section
new_desc="${existing}

---

## Kickoff Prompt

<generated prompt body>"

td task update "$id" --description "$new_desc"
```

**Caveats:**
- `td task update --description` REPLACES, not appends. Always read existing first, concat, then write.
- For multi-line descriptions, write the text to a file first, then substitute the
  file (avoids `$` expansion + quote escaping issues):
  ```bash
  cat > /tmp/desc.md <<'EOF'
  <existing description>

  ---

  ## Kickoff Prompt
  <prompt body>
  EOF

  td task update "$id" --description "$(cat /tmp/desc.md)"
  ```
  Do NOT inline the heredoc inside the substitution (`--description "$(cat <<'EOF' ... EOF)"`).
  `dcg` blocks that form (`heredoc.posix:eval-dynamic`) — it cannot statically parse a
  dynamically assembled launcher. `$(cat <file>)` on its own is fine.
- If description already contains `## Kickoff Prompt`, **replace** that section in place rather than appending a second one. Skill must be idempotent — re-running on a task should refresh, not duplicate.

#### Idempotency: stripping an existing kickoff section before appending

Concrete pattern. Read existing description, strip everything from `---` + `## Kickoff Prompt` onward, then append the new section.

```bash
# Get just the description body (skip td task view metadata header)
existing=$(td task view "$id" 2>/dev/null | awk '/^Description:/{flag=1; next} flag')

# Strip an existing kickoff block, if any. Matches the separator + heading.
# The pattern: optional leading blank line, then ---, blank, ## Kickoff Prompt, then everything after.
clean=$(printf '%s\n' "$existing" | awk '
  /^---$/ { sep=NR; next_is_kickoff=1; next }
  next_is_kickoff && /^## Kickoff Prompt/ { stripping=1 }
  next_is_kickoff && !/^## Kickoff Prompt/ && !/^$/ { 
    # not a kickoff — print the buffered separator and this line
    print "---"; print ""; print; next_is_kickoff=0; next 
  }
  !stripping && !next_is_kickoff { print }
')

# Compose new full description
new_desc="$(printf '%s\n\n---\n\n## Kickoff Prompt\n\n%s\n\n*Generated by todoist-kickoff-prompt*\n' "$clean" "$prompt_body")"

td task update "$id" --description "$new_desc"
```

The awk script handles three cases: (a) no existing kickoff → passes through unchanged; (b) existing kickoff at end → strips it; (c) `---` followed by something that *isn't* `## Kickoff Prompt` → preserves it (so we don't accidentally eat a real horizontal rule).

**Test the regenerate path before shipping batch updates** — feed in 1 task that already has a kickoff section, verify the output has exactly one `## Kickoff Prompt` heading.

Simpler alternative (less robust but fewer edge cases): treat `--- *Generated by todoist-kickoff-prompt*` as the unique end-marker and split on that. Requires every generated prompt to end with the marker (this skill does).

### 6. Report back

For each task processed, one line:

```
✓ 6abc... — Kickoff prompt generated (5 refs, 4 AC items)
✗ 6def... — Skipped: bare-title task, no description content to anchor on
```

End with: "Prompts printed above + appended to task descriptions. Open Todoist or paste from terminal to start work."

## Composability — calling from triage skills

**At the end of `todoist-inbox-triage` step 8 / `todoist-project-triage` step 13 (final summary):**

Surface this skill as the natural next step:

```
Final summary above. Want kickoff prompts for any of these? Run `todoist-kickoff-prompt` with the task IDs (auto-suggest will pick high-signal ones).
```

When the user says yes, hand over the candidate list (auto-suggest pre-filtered, or user-named IDs) — don't make them re-list every ID.

## Anti-patterns

- **Padding bare-title tasks.** If the description is empty or a single line, the prompt has nothing to anchor on. Refuse, ask user to enrich the task first.
- **Generating from list-view output.** `td task list` truncates. Always `td task view` per task.
- **Duplicate `## Kickoff Prompt` sections.** Re-running must replace in place.
- **Auto-suggesting then silently generating without confirmation.** User should see the candidate list and prune.
- **Hallucinating refs.** Only include files/beads/ADRs that are literally mentioned in the description. The prompt's value is *fidelity to user-written context*, not creative synthesis.

## Common Gotchas

- **`td task update --description` replaces.** Read existing first, concat, then write. Heredoc form avoids quote/`$` issues.
- **Multi-line descriptions in bash:** literal newlines inside double quotes work; `\n` does not. Heredoc with `<<'EOF'` (quoted EOF) prevents `$VAR` expansion in description text.
- **Closed tasks are still viewable by ID.** If a triage flow closed a rich task, you can still kickoff-prompt-extract via `td task view <id>` — but only if you saved the ID.
- **Markdown links in descriptions render in Todoist.** Use `[label](url)` for cross-refs; bare URLs are also clickable.

## What this skill is NOT

- Not a planner — it formats existing context, doesn't invent strategy.
- Not a session-starter — printing a prompt doesn't run anything.
- Not a substitute for rich task descriptions — garbage in, garbage out.
